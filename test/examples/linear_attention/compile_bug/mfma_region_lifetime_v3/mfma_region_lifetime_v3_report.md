# MFMA Region Lifetime v3 Report

## Summary

This report is generated by `profile_mfma_region_lifetime_v3.py`. It isolates independent pred/update MFMA regions in one minimal Avelang kernel. The key question is whether combined variants allocate/register-live closer to `max(pred_only, update_only)` or closer to `pred_only + update_only`.

### Summary Conclusion

This minimal repro does **not** support a generic compiler/backend bug where two independent sequential MFMA regions with fresh accumulators cause VGPR/AccVGPR to accumulate additively.

Key evidence:
Recommended model: GPT-5.5
Recommended reasoning effort: High

We have completed `mfma_region_lifetime_v3`. The result does NOT support a generic compiler/backend bug where two independent sequential MFMA regions additively accumulate VGPR/AccVGPR.

Important conclusion from v3:

* `update16_only`: VGPR=92, AccVGPR=84
* `pred32_only_sink`: VGPR=80, AccVGPR=184
* `pred32_then_update16`: VGPR=92, AccVGPR=172
* `pred32_two_regions_then_update16`: AccVGPR=172
* correctness passes for all variants
* dummy barrier and source lifetime hint do not improve resources

Therefore:
Do not continue investigating generic sequential MFMA lifetime overlap.
Do not re-debug old FullOp Pure CSE bug.
Do not work on v24/v23 production.
Do not investigate BF16 recurrence semantics.
Do not implement Triton-like block-dot lowering.

Find which Qwen-shaped source pattern causes the v28/v29 production kernel resource explosion. The issue is likely not independent sequential MFMA, but one of:

* MFMA32 accumulator unpack / pred_partial LDS staging;

* k/state/update staging;
* real pred->update data dependency;
* h/vn/global materialization;
* complex al.view / tensor layout / address generation;
* non-independent Qwen dataflow extending live ranges.

We need a Qwen-shaped feature ladder / delta-debugging suite.

Do not implement full Qwen correctness at every level. The goal is resource/lowering attribution. Still, where a tensor has a simple reference, check it.

Implement variants L0-L9. Each variant should be a separate JIT kernel or selectable variant, with a clear kernel name for rocprof regex.

L0 `pred32_mfma_only`

* Load Qwen-shaped W tile and state tile.
* Run MFMA32 pred only.
* Store tiny pred sink to global.
* No accumulator unpack to full pred_partial.
* Purpose: base MFMA32 cost.

L1 `pred32_unpack_to_pred_partial`

* L0 + unpack pred_acc[0..15] into `pred_partial` LDS with the same layout used by v29.
* Store a tiny sink so pred_partial is consumed.
* Purpose: cost of MFMA32 accumulator unpack and LDS writes.

L2 `pred32_unpack_reduce`

* L1 + reduce partial0 + partial1 into pred_o for at least a full tile or representative elements.
* No u load yet.
* Purpose: cost of pred_partial LDS reads/reduction.

L3 `pred32_ucorr_epilogue_no_store`

* L2 + load u and compute `u_corr = u - pred_o`.
* Do not write full global vn.
* Store tiny checksum/sink only.
* Purpose: cost of u global load + subtract without materialization.

L4 `pred32_vdecay_shared_stage`

* L3 + compute decay/simple decay and stage `v_decay_t_bf16[V, token]` into shared memory.
* Use Qwen-like `[V, token]` shared layout.
* Store tiny sink.
* Purpose: cost of v_decay_t shared staging.

L5 `pred32_vdecay_plus_k_stage`

* L4 + stage k_chunk into the shared layout needed by update.
* No update MFMA yet.
* Purpose: isolate k staging / view / shared layout cost.

L6 `pred32_vdecay_update16_one_ktile`

* L5 + perform update MFMA16 for only one K tile / small subset.
* No full state writeback.
* Purpose: first real pred->update dependent MFMA cost.

L7 `pred32_vdecay_update16_full_k_no_feedback`

* L6 extended to full K=128 update for one chunk.
* Write delta/state sink but do not feed it into next chunk.
* Purpose: full update cost without recurrence feedback.

L8 `pred32_update16_full_k_state_writeback`

* L7 + write state_after into state buffer / final_state layout.
* Still single chunk or no feedback.
* Purpose: state writeback cost and layout.

L9 `pred32_update16_with_h_vn_global_materialization`

* L8 + write h/vn-style global outputs similar to v29/v24 full path.
* Purpose: global materialization cost.

Optional L10 `two_chunk_feedback`

* Two chunks with feedback, only if implementation cost is reasonable.
* Purpose: see if recurrence itself changes resource/lowering, not just numerical error.

TASK 4: Interpret as compiler/lowering issue or source schedule issue
=====================================================================

For the biggest jump, classify it:

A. Compiler/lowering issue candidate:

* A small source construct leads to huge scalarized ISA.
* Example: a simple contiguous store becomes many address ops and scalar stores.
* Example: pred_acc unpack generates excessive address arithmetic.
* Example: shared view staging creates many ds_read/ds_write and blocks vectorization.
* Example: adding an unused-but-live shared tensor causes register/lifetime explosion.

B. Source schedule issue:

* Resource grows as expected because we genuinely add many MFMA/update/global stores.
* No single lowering pathology found.
* Then the problem is Qwen source schedule is too large for one kernel, not a small compiler bug.

C. Mixed:

* Some resource growth expected, but a specific source pattern is badly lowered and could use a small helper.

For classification, cite exact counters and ISA.

## Compiler/Backend Audit Interpretation

1. `al.full` lowering:
   - `FullOp` is defined at `lib/Dialect/AveLang/IR/AveLangOps.td:134` as `AveLang_Op<"full", []>`, so it no longer has the old `[Pure]` trait.
   - `FullLoweringPattern` in `lib/Dialect/AveLang/Transforms/lower_ave_lang_to_memref_pass.cc` lowers `FullOp` by creating a private-memory `memref::AllocaOp`, broadcasting the scalar fill value into a vector, storing it into a flattened 1D view, and replacing the `FullOp` result with that memref.

2. FullOp purity/freshness:
   - The old FullOp/Pure CSE bug is not present in this tree: `FullOp` has no `[Pure]`.
   - Before lowering, the op is therefore not advertised as a pure/speculatable value producer. After lowering, each `FullOp` creates a private `alloca`.
   - The repro correctness confirms fresh update accumulators are not corrupted by preceding pred accumulators.

3. Private tensor lowering:
   - Private tensors/accumulators created by `al.full` lower through private address-space memrefs/allocas before later optimization.
   - MFMA accumulator tensors are source-level `al.full((4,), ...)` or `al.full((16,), ...)` values that lower through this private allocation path and are later optimized/SROA'd into registers/AGPRs when possible.

4. Allocation hoisting:
   - `lib/Dialect/AveLang/Transforms/allocation_op_interface_impl.cc` explicitly says GPU-kernel stack variables are hoisted to entry/block scopes to enable LLVM SROA.
   - The pipeline also runs `createHoistAllocaPass`, MLIR `BufferHoistingPass`, and `BufferLoopHoistingPass`.
   - So private allocations can be hoisted, but this repro shows hoisting does not by itself force additive AccVGPR for independent pred/update regions.

5. Lifetime end/dealloc:
   - Grep found no obvious explicit `lifetime.end`, `dealloc`, or `alloca_scope` mechanism in the relevant pass path.
   - Lifetime is therefore mostly inferred by downstream optimization/register allocation after hoisting and SROA.

6. MFMA lowering:
   - MFMA intrinsics are declared in `lib/IR/Intrinsics/amdgpu_mfma_signatures.h`.
   - `mfma_16x16x16_bf16_f32` maps to `rocdl_mfma_f32_16x16x16bf16_1k`.
   - `mfma_32x32x8_bf16_f32` maps to `rocdl_mfma_f32_32x32x8bf16_1k`.
   - ISA confirms expected instruction counts for each variant: e.g. `pred32_then_update16` contains `16` MFMA32 plus `32` MFMA16 instructions.

7. View/alias caveat:
   - The repro uses `al.view` for packed BF16 fragments, but the independent pred/update variants do not show additive register accumulation.
   - This does not rule out view/alias conservatism in larger kernels with persistent state and more complex epilogues; it only says the simple independent case is clean.

8. Relevant pass sequence:
   - The observed path includes AveLang-to-intrinsic lowering, canonicalization, CSE, alloca hoisting, buffer hoisting, AveLang-to-memref lowering, GPU outlining, OneShotBufferize, SCF/control-flow lowering, affine/index lowering, and canonicalizer/CSE again.
   - These passes can extend allocation placement, but the measured resource behavior here remains non-additive for independent sequential MFMA regions.

IR dump note: no stable Python-level option for dumping pre/post-lowering MLIR was found during this pass. The report therefore uses source grep, HSACO dumps, ISA disassembly, and rocprof metadata rather than MLIR snapshots.

## Direct Answers

1. Does `pred_only` already have high AccVGPR?
   - Yes for MFMA32: `pred32_only_sink` has `AccVGPR=184`.
   - MFMA16 pred-only is lower but still nontrivial: `pred16_only_sink` has `AccVGPR=132`.

2. Does `update_only` already have high AccVGPR?
   - No relative to pred32: `update16_only` has `AccVGPR=84`.

3. Does combined pred+update become high only when both are present?
   - No. `pred32_then_update16` has `AccVGPR=172`, lower than `pred32_only_sink=184` and far below the additive sum `268`.

4. Do h/vn stores extend accumulator lifetime?
   - This minimal repro intentionally has no h/vn stores, so it cannot answer that directly. Prior Qwen-side evidence must be used for that question.

5. Does decay extend accumulator lifetime?
   - This repro intentionally has no decay. It cannot answer decay-specific lifetime behavior.

6. Is `AccVGPR=212` caused by unavoidable h1/h2 state fragments or poor reuse between `pred_acc` and `update_acc`?
   - The minimal independent-region evidence argues against poor reuse between fresh independent pred/update accumulators as the standalone cause.
   - It suggests v28's `AccVGPR=212` is more likely tied to the full kernel's state geometry/dataflow/epilogue/persistent fragments than to generic sequential MFMA lowering.

7. Did dummy barriers help?
   - No. `pred32_then_update16_with_dummy_barrier` has the same `VGPR=92`, `AccVGPR=172`, and same MFMA/VALU/VMEM/LDS counts as `pred32_then_update16`.

8. Did source-level lifetime hint help?
   - No. Overwriting the source `pred32_acc` after the sink did not reduce AccVGPR; it slightly increased VALU/SALU by two instructions.

## Initial Interpretation Checklist

- `update16_only` is the correctness baseline for update output.
- `pred32_then_update16` should be compared against `max(pred32_only_sink, update16_only)` for VGPR/AccVGPR/Scratch.
- If barriers or source lifetime hint do not reduce resources, evidence points away from simple source ordering and toward lowering/register-lifetime behavior.
- Static max VGPR/ACC index extraction is best-effort only; rocprof `VGPR_Count`/`Accum_VGPR_Count` is authoritative.
